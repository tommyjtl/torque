# Classic DOOM on the UNO Q with a Mojo engine

**Design draft · 2026-11-18**

Choose a **Mojo software renderer** as the reference implementation. Add an **Adreno OpenGL renderer** selectable at startup in the same game. Both consume the same level, simulation state and player commands. An episode saved with one renderer must resume with the other.

The proposed standalone Linux executable uses Mojo for the main loop, input mapping, WAD reading, simulation, audio mixing, menus, saves and rendering decisions. Native libraries provide windowing, input events, sound output and GPU access. In CPU mode Mojo produces the scene pixels. In GPU mode the rasterizer and GLSL shaders draw the scene. Python is optional for an external Torque integration. The normal game and its keyboard and mouse controls should run with Python absent.

## What counts as the game

The proposed first campaign acceptance target is **the original DOOM Episode 1**, including its secret map. A player should be able to start a game, change levels, save, quit, reload and finish the episode with its enemies, pickups, doors, switches, HUD, automap, sounds, music and intermissions working. This proves an episode, not the entire game. Full campaign acceptance extends those checks to every episode in the selected DOOM I edition, including edition-specific level transitions, boss triggers and finales. Use a user-supplied original IWAD (the game-data archive) for those checks. Develop small redistributable map fixtures for routine tests. Freedoom is a separate playable content option with its own compatibility checks. Use the licensing terms and notices appropriate to any ported id source, and keep commercial IWAD data outside the repository. [Original engine release](https://github.com/id-Software/DOOM) · [Freedoom game data](https://freedoom.github.io/about.html)

The priority is a complete Mojo game loop and a playable single-player campaign. Multiplayer, arbitrary mods and bit-exact compatibility with original demo recordings are separate scope decisions. Replaying **our own** input commands is required from the start so the two renderers can be compared fairly.

## One game, two ways to draw a frame

Mojo advances the world at **35 game ticks per second** using a monotonic clock and a fixed time step. Each tick consumes one player command. The simulation alone updates positions, sector heights, switches, enemies, random state and audio cues. Rendering may run more often and interpolate camera and object poses. Dropping a render frame must never drop a game command. Both builds use the same simulation code and serialization format. [Original tick rate](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/doomdef.h)

The WAD loader decodes map geometry, BSP nodes and subsectors, sector connectivity, texture patches, flats, sprites, palettes and light tables once. Each backend receives immutable level resources at map load and a read-only view of dynamic state for each frame. Keep visibility and draw ordering private to the renderer. Passing the CPU renderer's finished wall columns to the GPU would prevent the GPU backend from taking advantage of its own depth buffer.

| | CPU software renderer — first implementation | Adreno GPU renderer — second implementation |
|---|---|---|
| World | Traverse the map BSP front to back. Clip wall segments and draw textured columns. Collect visible floor and ceiling regions and draw horizontal spans. Handle sky, masked walls, sprites and their occlusion. | Build wall and flat meshes from the same map, including holes and two-sided openings. Batch by texture/material, depth-test opaque geometry, handle masked surfaces and billboard sprites, and update geometry affected by moving doors or lifts. |
| Appearance | Start with a 320×200 indexed framebuffer, palette and light-table lookup, and a final aspect-correct 4:3 presentation on the 640×480 screen. Keep HUD and menu coordinates in the original logical space. | Use the same palette, lighting rules, animation frames, camera convention and HUD layout for comparison. First test at matching resolution and filtering. Offer native 640×480 and antialiasing as separately measured options. |
| Ownership | Mojo writes every world pixel. A native window library presents the buffer. A driver-assisted final blit may still use the GPU. | Mojo owns the draw loop and resource lifetime through a C graphics interface. GLSL handles per-vertex and per-pixel work. Direct Mojo compute kernels for Adreno are not a dependency of this path. |

For renderer selection, propose `--renderer=cpu` as the initial default and `--renderer=gpu` for explicit GPU runs. An explicit GPU request should report the actual device, driver, context and failure reason if it cannot start. A later `auto` mode may visibly select CPU fallback. Performance results always identify the backend that actually ran. [Original BSP renderer](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/r_main.c) · [Previous on-board Mojo software rendering](../../projects/mojo-turntable-2026-11-15/README.md)

## Native input and a small API

**Mojo can receive keyboard presses, mouse clicks and relative mouse movement.** A Linux window library receives the OS events. Mojo calls its C API and maps the events to game actions. SDL2 is the proposed first platform library because one foreground window can handle input and present either a software buffer or an OpenGL scene. Inventory the installed standalone ARM64 library, ABI and available context before committing to it. Previous pygame runs establish SDL-backed graphics via that package. A library inside a Python wheel is insufficient evidence of a supported standalone link. [Mojo foreign function interface](https://mojolang.org/docs/std/ffi/) · [SDL event polling](https://wiki.libsdl.org/SDL2/SDL_PollEvent) · [SDL relative mouse mode](https://wiki.libsdl.org/SDL2/SDL_SetRelativeMouseMode)

Keep game-facing interfaces small. These are proposed contracts, not installed commands or Mojo syntax.

| Interface | Contract |
|---|---|
| `poll_input() → input events` | The platform layer pumps the focused window on its owning thread. Return key/button down and up, relative mouse delta, focus change and quit. A thin C shim may normalize SDL's tagged event union into fixed-width records for Mojo. The shim contains no game rules. |
| `step(command) → world update` | Mojo maps input to held movement, accumulated turn delta and action edges for the next tick. Consume each edge and mouse delta once, even when a rendered frame contains multiple ticks. Expose this same command boundary to a replay harness or a future external controller. |
| `renderer.load(level)`, `renderer.draw(frame)`, `renderer.close()` | Both backends implement the same internal lifecycle. Static resources are owned until level unload. A frame borrows its view of the world only for the call. Renderer-owned buffers, textures and handles stay out of save files. |

The standalone game can keep all three interfaces internal. If another local program needs control, the proposed public surface is just `submit_command(tick, command)` and `read_status()` (current tick, map, pause state and active renderer). The host would submit to the next unprocessed tick and receive an error for stale commands. Mojo continues to own the clock. Defer binding and ABI choices until there is an actual embedding caller.

Start with WASD or arrow keys, relative horizontal mouse movement to turn, left click to fire, Space to use, and a configurable keyboard/K0 mapping. Ordinary K0 numpad keys can arrive as desktop events. Reserve **0 / KP0 for exit** per the Torque workspace convention. Show the controls in the menu. Capture relative mouse motion during play, release it in menus or on focus loss, clear held inputs on focus loss, and discard stale motion when play resumes. One physical press must generate one action. A later optional K0 knob adapter can use Torque's existing Python keypad API and lease if the desktop does not expose the needed control. Give each input one owner and pass the same logical commands to Mojo. [Torque keypad API](../../agent/skills/uno-q-input/references/keypad-api.md)

## Build and first playable milestone

1. **Prove the executable and peripherals.** Build on the Mac for Linux ARM64/Cortex-A53 and link with a target toolchain. Our prior cross-compiled CPU kernels ran on the UNO Q. Its native Mojo 1.2.0 compiler failed at startup, and the earlier tests did not establish compatibility for all Mojo runtime features. On the board, inspect the executable's dependencies, open a window, draw a CPU framebuffer, play a short generated tone and exercise key down/up, relative mouse turn and left click. Confirm focus/quit cleanup. Run this standalone with no Python process. If packaging or linking fails, record the exact dependency. A future Torque launcher can delegate to a reviewed native executable while preserving existing tool permissions and process ownership. [Cross-compilation evidence](../../projects/mojo-exploration/CROSS-COMPILATION.md) · [Mojo target/linker guide](https://mojolang.org/docs/tools/compilation/) · [Torque native integration design](2026-11-01-opt-in-mojo-projects.md)
2. **Make a room playable on CPU.** Load a small redistributable test WAD with two sectors, a door, a sprite and a level exit. Walk, collide, turn, open the door and finish the map. A save made before opening the door must restore its original state. Then try E1M1 from a user-supplied IWAD. Verify textured walls, flats, sky, sprite occlusion and 4:3 framing. This is the first playable slice.
3. **Draw that same room on the GPU.** Feed the identical level and command recording to the Adreno backend. Check door motion, texture alignment, sprite masking and HUD placement against reference viewpoints. Load a CPU save in GPU mode and a GPU save in CPU mode. Resolve differences before adding content.
4. **Complete the campaign systems.** Add the remaining actor and weapon states, sector specials, moving platforms, damage, pickups, secrets, difficulty settings, automap, menus, sound effects, music playback and intermissions. Exercise each new behavior in a small fixture and an original level that depends on it. Record episode and edition coverage separately.

## How we decide whether a backend works

- **Gameplay parity.** Run both backends with the same IWAD identity, starting state, RNG seed and tick-command trace. Hash canonical simulation state at agreed ticks and after save/reload. Require matching state hashes even when render cadence differs. Use visual checkpoints for renderer correctness, allowing differences from filtering and antialiasing.
- **Performance.** Measure the same route through a corridor, an open room with sprites, and a moving-sector scene. Compare matched-resolution CPU/GPU first, then compare the intended display modes. Record build, resolution, driver, filtering, warm-up, median/p95 frame interval, missed simulation ticks, process CPU and peak RSS. Aim for sustained 35 simulation ticks/s. A 60 Hz render loop on the board's display is a performance target. Game FPS is still unmeasured.
- **Usability.** Check with the physical keyboard, K0 and mouse that turning continues at screen edges, a click acts once, movement stops on release or focus loss, and quitting releases input, audio and graphics resources. Record physical observations separately from synthetic events and software screenshots.

**Open decisions.** Select the original DOOM I edition for final campaign acceptance and decide later whether exact original demo playback is a goal. The first implementation decision is smaller: establish a standalone window/input/audio path on the validation board, then build the CPU reference room. The board was unreachable during this design pass, so current platform-library availability remains an explicit first check.
